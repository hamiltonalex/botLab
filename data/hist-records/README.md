# Восстановленные записи рынка

Здесь лежат ГОТОВЫЕ записи, на которых считаются офлайн-отчёты схемы продавца
(`npm run hist:sellhedge`, `npm run replay:sellhedge`, `npm run eval:sell`). Они производны от
`data/deribit-cache/` и пересобираются командой `npm run hist:build`, но сборка пятилетнего окна
занимает около двадцати минут и 12 ГБ оперативной памяти на пике, поэтому результат положен в
репозиторий: воспроизводимость отчёта не должна упираться в ожидание.

Формат - тот же, что пишет живой сканер (`scan-records/*.ndjson`, суточные файлы), поэтому скрипты
читают эти каталоги без единой правки:

```
npm run hist:sellhedge -- --dir data/hist-records/rec-5y-maxdays30-logm045 \
  --funding data/deribit-cache/funding/btc-perpetual-1h.json --gate-sweep --zones
```

## Что внутри

| каталог | окно | потолки восстановления | объём | чем снята |
|---|---|---|---|---|
| `rec-5y-maxdays30-logm045/` | 2021-08-09 .. 2026-08-12, 43919 часовых снимков | срок ≤ 30 сут, \|ln(K/F)\| ≤ 0.45 | 2.5 ГБ | `hist:build --from 2021-08-09 --to 2026-08-13 --max-days 30 --max-logm 0.45` |
| `rec-1y-default-caps/` | 2025-08-16 .. 2026-08-08, 8592 снимка | срок ≤ 90 сут, \|ln(K/F)\| ≤ 0.6 (по умолчанию) | 717 МБ | `hist:build --from 2025-08-16 --to 2026-08-09` |

Каданс восстановления часовой (`--step-min 60`) у обеих. Он НЕСУЩИЙ: паспорт соответствия меряет
каданс решения 4 ч как ×26.5 против ×46.5, то есть разреженная запись описывает другую схему,
а не ту же самую подешевле.

## Почему у пятилетней записи потолки срезаны, и почему это не влияет на результат

Полное окно с потолками по умолчанию не помещается в память машины сборки. Срез безопасен по
построению: схема живёт в окне срока 336-672 ч (14-28 суток) и на дельте около 0.45, то есть у
самых денег, - всё это внутри 30 суток и 0.45 по логмани. Крылья ±1σ, по которым считается скос,
на этих сроках лежат примерно в 0.11-0.13 логмани.

Утверждение проверено, а не объявлено: год 2025-08-16..2026-08-09 собран ДВАЖДЫ - с потолками по
умолчанию и со срезанными - и книги сделок сверены построчно:

```
npm run hist:sellhedge -- --dir <A> --book a.tsv --book-lots 1
npm run hist:sellhedge -- --dir <B> --book b.tsv --book-lots 1
node scripts/compare-books.mjs --a a.tsv --b b.tsv
```

Результат: 16 сделок из 16 совпали по всем двенадцати столбцам - инструмент, вход, выход, лоты,
залог, перекладки, оборот, премия, хедж, издержки, фандинг, итог. Каталог `rec-1y-default-caps/`
оставлен в репозитории именно ради этой сверки: без него утверждение снова стало бы словом.

## Что на этих записях посчитано

Прогон 2026-08-24 по пятилетней: база 84 сделки, ×45.64 при просадке 13.5%, средняя сделка 4.90%
залога, вне рынка 0.5% времени. Перебор входных гейтов (`--gate-sweep`): ни одна из девяти клеток
не выше базы, лучшая ×33.38. Разрез по зоне продавца (`--zones`): 26 сделок из 84 открыты в худшей
зоне, они дали 3.76% за сделку при просадке 7.6%; цепочка же, торгующая ТОЛЬКО эту зону
(`--gate "ivrv<0"`), даёт 59 сделок, 2.71% и просадку 26.7%. Разбор различия - в шапке
`src/engine/otmscan/sell-scan.js`.

## Границы

`bid/ask` в этих записях МОДЕЛЬНЫЕ: истории котировок Deribit не хранит, спред переносится моделью
`hist-cost.js` (шкала пунктов IV, множитель 1). Сверка с живой записью даёт занижение круга на 6% в
рабочей полосе дельты - отсюда дефолт `--spread-scale 1.10` у отчёта. Глубины стакана в истории нет
вовсе, поэтому санитария инструмента на прогоне записи выключается настройкой, а не веткой кода.
